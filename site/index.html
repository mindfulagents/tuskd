The elephant that remembers

One binary gives your agent swarm a shared, durable memory.

tuskd is a local memory daemon for AI agents: a human-readable Markdown vault, hybrid search, MCP-native tools, per-agent keys and grants — and an intelligence loop that turns raw experience into shared, validated, versioned knowledge.

$ curl -fsSL https://get.opentusk.ai | sh
Quickstart — 5 minutes How it works

01 · Install

Install tuskd

tuskd ships as a single static binary with no runtime dependencies. The installer detects your platform, downloads the latest release, verifies its SHA-256 checksum, and installs to ~/.local/bin. It never asks for sudo.

shell
curl -fsSL https://get.opentusk.ai | sh

Options via environment variables: TUSKD_INSTALL_DIR to change the destination, TUSKD_VERSION to pin a release.

shell
curl -fsSL https://get.opentusk.ai | TUSKD_VERSION=v0.1.0 sh

Every release is immutable and stays available at get.opentusk.ai/releases/<version>/…, so pinned installs are reproducible.

shell
# Rust stable toolchain required
cargo build --release
install -m 0755 target/release/tuskd ~/.local/bin/

Building from source requires access to the repository (not yet public).

shell
V=$(curl -fsSL https://get.opentusk.ai/releases/latest.json | sed -n 's/.*"version": *"\([^"]*\)".*/\1/p')
curl -fsSLO "https://get.opentusk.ai/releases/v$V/tuskd-v$V-aarch64-apple-darwin.tar.gz"
curl -fsSLO "https://get.opentusk.ai/releases/v$V/tuskd-v$V-aarch64-apple-darwin.tar.gz.sha256"
shasum -a 256 -c "tuskd-v$V-aarch64-apple-darwin.tar.gz.sha256"
tar xzf "tuskd-v$V-aarch64-apple-darwin.tar.gz"

Checksums are published next to every artifact. The installer script performs this same verification automatically.

02 · Quickstart

From zero to remembering in five minutes

1

Initialize a vault

A vault is a directory of Markdown files — one file per memory record. The files are the source of truth; everything else is derived and rebuildable.

shell
mkdir team-vault && cd team-vault
tuskd init
2

Create an agent

Every agent gets an ed25519 keypair, a bearer token, and explicit grants per scope. The token and paste-ready MCP configs are printed exactly once — store them now.

shell
tuskd agent create hermes-dev \
  --read project:demo,user \
  --write project:demo \
  --promote project:demo
output
agent created: hermes-dev

token: tusk_…   (shown ONCE — store it now)

private signing key stored at: .tusk/keyring/keys/hermes-dev.pem
  (0600, excluded from export; reserved for signed auth / SEAL / Walrus)

MCP config (stdio):
  {"command": "tuskd", "args": ["mcp", "--agent", "hermes-dev"]}
MCP config (streamable HTTP):
  {"url": "http://127.0.0.1:7477/mcp",
   "headers": {"Authorization": "Bearer tusk_…"}}
3

Start the daemon

Exactly one tuskd process owns the index and file-watcher. It serves MCP over HTTP on 127.0.0.1:7477 and over a Unix socket. -d detaches it (log at .tusk/daemon.log); tuskd stop shuts it down gracefully, tuskd restart -d cycles it after an upgrade.

shell
tuskd start -d
curl -s http://127.0.0.1:7477/status
4

Connect your agents

One command writes your client's MCP config, creates the agent identity if needed, and verifies the handshake. Works for Claude Code, Claude Desktop, Cursor, Codex, and VS Code — see Agent setup for details and generic clients.

shell
tuskd agent setup claude-code
5

Watch memory accumulate

Agents write with memory_write and recall with memory_search. The CLI works alongside the daemon — commands route through it, never a second writer.

shell
tuskd status
tuskd search "env parity" --scope project:demo
6

Run the loop

Contested writes land in a review queue; procedures that keep succeeding graduate into agent-loadable SKILL.md files.

shell
tuskd review list
tuskd graduate
7

Open the dashboard

Status, search, memories, the review queue, agents, and housekeeping — in your browser, authenticated with a one-per-run operator token.

shell
tuskd dashboard

03 · Agent setup

Wire up your MCP clients

The fast path is tuskd agent setup <client>: it merges an opentusk entry into the client's existing config (taking a backup first — nothing else in the file is touched), creates the agent identity with sensible default grants if it doesn't exist, and verifies a real MCP handshake before it reports success. Re-running it is a no-op; --remove takes the entry back out.

shell
tuskd agent setup claude-code   # also: claude-desktop | cursor | codex | vscode
tuskd agent setup list          # what's configured, and where each config lives

Under the hood there are two transports: stdio (the client launches tuskd mcp, which proxies to the daemon or runs embedded when none is running — no token needed) and streamable HTTP (bearer-token auth against the local daemon; --http). The tabs show what gets written — or what to paste manually into any other client.

shell
# current project only
claude mcp add tuskd -- tuskd mcp --agent hermes-dev

# or shared via .mcp.json in the repo
claude mcp add --scope project tuskd -- tuskd mcp --agent hermes-dev

stdio needs no token — identity comes from --agent, and the session proxies to the running daemon over its Unix socket.

claude_desktop_config.json
{
  "mcpServers": {
    "tuskd": {
      "command": "tuskd",
      "args": ["mcp", "--agent", "hermes-dev"]
    }
  }
}
.cursor/mcp.json
{
  "mcpServers": {
    "tuskd": {
      "command": "tuskd",
      "args": ["mcp", "--agent", "hermes-dev"]
    }
  }
}
mcp config
{
  "url": "http://127.0.0.1:7477/mcp",
  "headers": { "Authorization": "Bearer tusk_…your token…" }
}

The bearer token is printed once at tuskd agent create. Every request is authenticated; the endpoint is a single stateless POST /mcp.

Scopes and grants

Every memory record lives in exactly one scope, and every tool call passes one ACL choke-point:

  • agent:<id> — the agent's private scope. Always writable by its owner.
  • project:<name> — shared team knowledge for one project.
  • user — knowledge about the human the agents work for.

Grants are explicit and per-scope: read (search & fetch), write (direct writes), promote (submit candidates through the gate into shared scopes).

shell
tuskd agent grant hermes-dev read project:other
tuskd agent list
tuskd agent revoke old-agent
A useful pattern: give worker agents write only on their own scope and promote on the project scope — so everything shared has passed the gate — and give read-only observers (dashboards, review bots) just read.

04 · Concepts

How tuskd thinks about memory

One machine, one daemon, one writer. A single tuskd process owns the SQLite index and the file-watcher; stdio sessions proxy to it over a Unix socket, and the CLI routes through it too. If no daemon is running, commands run the core embedded under the same advisory lock — so there is never a second writer.

VAULT

Files are the truth

One Markdown file per memory record, with strict frontmatter. Grep it, diff it, back it up. The SQLite index is derived and rebuildable at any time with tuskd index rebuild.

THE GATE

Nothing enters shared memory unchecked

Every promotion runs dedup → contradiction probe → per-scope policy → commit, or lands in the review queue. Agents can't silently overwrite what the team knows.

GRADUATION

Experience becomes skills

Success/failure telemetry feeds ranking. Procedures that keep working graduate into agent-loadable SKILL.md files — proven knowledge, packaged for reuse.

BITEMPORAL

Nothing is edited in place

Corrections supersede; history stays. as_of queries answer "what did we believe then?" — essential when yesterday's run acted on yesterday's beliefs.

06 · FAQ

Questions you'll have

Why exactly one daemon per vault?

SQLite gets one writer; so does the vault. tuskd enforces this with an advisory flock on .tusk/lock that dies with the process — stale locks can't wedge the vault. Everything else (stdio sessions, CLI commands, the dashboard) routes through the owner over its Unix socket, so you get concurrency without corruption.

I lost an agent's token. Now what?

Tokens are shown once and never stored in recoverable form. Revoke the agent and re-create it with the same grants: tuskd agent revoke <id>, then tuskd agent create <id> --read … --write …. Its memories stay — scopes belong to the vault, not the credential.

Where does my data actually live?

In the vault directory you initialized: one Markdown file per record under memory/, skills under skills/, and derived state under .tusk/. Nothing leaves your machine — tuskd binds to localhost only and makes no outbound network calls. Back up the vault by copying the directory, or use tuskd export.

I edited vault files by hand while nothing was running. Is the index stale?

No — both daemon start and embedded open run an idempotent index rebuild, so offline edits are always picked up. You can also force it any time with tuskd index rebuild.

Can two machines share a vault?

v0 is deliberately single-machine. Move knowledge between machines with tuskd export archive.tar.gz and tuskd import archive.tar.gz. Don't put a live vault on a network filesystem — advisory locks and file-watchers are unreliable there.

macOS says the binary "cannot be verified"?

Releases aren't codesigned yet. Installs via curl … | sh aren't quarantined, so this only appears if you downloaded a tarball with a browser — clear it with xattr -d com.apple.quarantine ~/.local/bin/tuskd. Signing and notarization are on the release roadmap.
